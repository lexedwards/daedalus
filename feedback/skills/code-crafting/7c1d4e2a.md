# Feedback: Skill - code-crafting

## Evaluation Scope

This is a theory review, not an empirical evaluation. No prompt set, rubric, repeated trials, or no-skill baseline was provided, so the scores estimate design quality on a five-point scale rather than measured outcome uplift.

## Summary

The skill gives a coherent, durable engineering workflow: trace the real path, choose a small vertical slice, test observable behavior, fix shared root causes, and verify before stopping. Its safety guidance is particularly useful because it explicitly protects validation, security, accessibility, data-loss prevention, and error handling from over-aggressive simplification.

The main weakness is that the entry point is large and assumes implementation work even though its trigger includes code review. Repeated guidance and a few conditional instructions can increase token and tool cost while allowing different agents to follow different workflows for the same prompt.

## Findings

### High: The review trigger has no compatible review workflow

The frontmatter says to use the skill when reviewing code, but the craft loop, `Done Means`, and `Output Style` are written for making a change. A review-only task has no implementation slice, failing test, or `Implemented` result to report. This can cause unnecessary edits or make an agent force review work into an implementation-shaped response.

Either remove general code review from the trigger or add a separate review branch with review-appropriate trace, evidence, findings, and output steps. The trigger should also distinguish design review from analysis-only code review.

### High: The entry point spends too much context repeating the same constraints

Small changes, public behavior, avoiding speculative abstractions, scope discipline, and verification recur in `Core Principles`, the numbered workflow, `Testing Guidance`, `Scope Discipline`, `Verification`, and `Done Means`. The module-design and test taxonomy sections are useful, but loading all of them for every coding task weakens context efficiency.

Keep the entry point to trigger rules, the core loop, and non-negotiable safety constraints. Move detailed module-design and testing advice into progressive-disclosure references, or remove duplicated wording.

### Medium: Test and verification requirements do not have a clear precedence

The craft loop presents `TDD: RED` as a standard phase, while the detailed text qualifies a failing check with “when practical” and later exempts trivial one-liners from new tests. Verification asks for both a narrow check and broader verification after each slice, but does not define when the broader pass is unnecessary. Missing harnesses are mentioned only as a gap to state, not as an explicit workflow choice.

State one priority order: use red-green-refactor for behavior changes when a runnable harness exists; otherwise use the cheapest durable check available and state the gap. Require broader checks only when affected boundaries or regression risk justify them.

### Medium: The mandated output format is too implementation-specific

`Implemented / Verified / Skipped` is useful for a completed code change but does not fit a design review, investigation, blocked task, or a deliberate decision not to edit. The `Skipped` placeholder can also encourage boilerplate or duplicate the host harness’s response format.

Make the format conditional on implementation work, or replace it with a neutral outcome-and-evidence rule that works for both changes and reviews.

## Recommended Next Evaluation

After clarifying the review and verification branches, run an ablation across small bug fixes, feature slices, refactors, design reviews, analysis-only code reviews, documentation edits, and tasks with no test harness. Repeat each prompt with and without the skill, scoring correctness, unnecessary edits, test relevance, tool calls, tokens, latency, and procedural compliance. Include negative prompts to verify that documentation and review-only work do not trigger an implementation workflow.
