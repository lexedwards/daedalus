# Feedback: Skill - ideation

## Evaluation Scope

This is a theory review, not an empirical evaluation. No prompt set, rubric, repeated trials, or no-skill baseline was provided, so the scores estimate design quality on a five-point scale rather than measured outcome uplift.

## Summary

The skill is compact and promotes several useful behaviors: investigate facts rather than asking the user to supply them, ask one question at a time, recommend an answer, challenge terminology, and test ideas against concrete scenarios. These are durable principles with very low context cost.

Its main weakness is lack of control over the interaction. "Relentlessly," "every aspect," and "each branch" create an unbounded interview with no prioritization or stopping rule. The skill also instructs the agent to update documentation while ideas are still crystallising, without requiring explicit permission, a confirmed decision, or a destination. There is no final synthesis that makes shared understanding observable.

## Findings

### High: The interview is intentionally unbounded

The workflow requires interviewing the user "relentlessly" about "every aspect" and resolving "each branch of the design tree." Most idea spaces contain effectively unlimited branches, including low-impact hypotheticals. Asking every question one at a time compounds latency and can prevent the skill from ever reaching a useful result.

Define convergence around material decisions instead: establish the user's objective and desired depth, identify the highest-risk unknowns, resolve only questions that materially affect the idea, and stop when those decisions are settled, deferred, or explicitly out of scope. Allow the user to end or narrow the exploration at any point.

### High: Documentation can be changed before decisions are confirmed

The description says to update documentation "as decisions crystallise," and the pitfalls require terminology and understandings to be captured inline with discussion. Ideation is exploratory: candidates may be revised or rejected later. The skill does not require the user to request edits, confirm the decision, identify an authoritative document, or review the proposed wording.

Do not mutate project documentation by default during ideation. First recap the proposed decision and obtain confirmation. Update a named authoritative artifact only when the user requested durable capture or approves the edit; otherwise keep the synthesis in the conversation and hand off to the appropriate capture workflow.

### Medium: Shared understanding has no observable completion artifact

The skill names shared understanding as its goal but never requires a final summary. The agent and user can finish a long interview with different memories of the decisions, assumptions, deferred questions, and rejected alternatives.

End with a concise synthesis of the objective, agreed decisions, terminology, assumptions, unresolved questions, and explicit out-of-scope branches. Ask the user to confirm that synthesis before treating ideation as complete.

### Medium: Trigger and handoff boundaries are underspecified

"Discuss an idea" is broad enough to trigger on casual brainstorming, requests for options, requirements capture, design work, and implementation planning. This repository already has separate `requirements-capture`, `decision-capture`, and `implementation-planning` skills, but ideation does not define when to stop and hand off.

Narrow the trigger to open-ended or decision-heavy exploration where the user wants interactive challenge. Add negative boundaries for requests that already specify a concrete artifact or task breakdown, and define handoffs after the idea is confirmed rather than blending capture or planning into the interview.

### Medium: Terminology guidance can prematurely impose a convention

The skill says to call out conflicts immediately and use "precise canonical terminology." Many domains have multiple valid vocabularies, and project-specific language may deliberately differ from an industry convention. The instructions do not require checking local sources before declaring a conflict or preserving the user's chosen language after discussing the tradeoff.

Check existing project and domain usage first. Explain the ambiguity or conflict, recommend a term with a reason, and let the user decide. Reserve "canonical" for cases with an identified authoritative source. Also correct "vague or overloaded teams" to "vague or overloaded terms."

### Medium: Evidence gathering lacks a bounded source policy

The workflow says to query an LLM wiki when available and explore the codebase when it can answer a question, but it does not define how availability is determined, which sources take precedence, or when investigation is worth its cost. An agent may search broadly before each question or treat stale wiki content as authoritative.

Use current code and named authoritative project documents for claims about existing behavior. Consult a configured wiki only when it is relevant, and distinguish its historical context from current implementation. Investigate only questions that materially affect the next decision.

## Rubric Notes

| Measure | Assessment |
| --- | --- |
| Trigger quality | Interactive idea exploration is recognizable, but "discuss an idea" is broad and overlaps artifact capture and planning workflows. |
| Outcome uplift | Focused questioning, recommendations, and scenario testing should improve weak brainstorming, but uplift is unmeasured and the missing synthesis can erase gains. |
| Reliability | There is no prioritization, stopping rule, confirmation checkpoint, or defined final output, so runs can vary substantially in length and completeness. |
| Efficiency | The skill text is short, but exhaustive one-at-a-time questioning and loosely bounded repository research can create high latency and tool use. |
| Procedural compliance | Several actions are explicit, yet "every aspect" and "each branch" are practically impossible to satisfy, while documentation updates lack preconditions. |
| Safety | Validating claims is protective, but unsolicited edits can persist unsettled decisions and terminology as project truth. |
| Context efficiency | Excellent: the entry point is small, direct, and has little duplication. |
| Source alignment | The skill favors evidence, but does not establish source authority, freshness, or a reliable protocol for detecting and querying an LLM wiki. |
| Maintainability | The structure is simple and easy to update; a few vague terms and copy errors reduce precision. |
| Durability | Collaborative questioning, evidence checking, precise language, and scenario analysis are lasting practices; "relentless" exhaustiveness is not. |

## Recommended Next Evaluation

After adding convergence, confirmation, and handoff rules, run an ablation across vague product ideas, technical design choices, casual brainstorming, terminology disputes, claims contradicted by code, requests with existing documentation, and prompts that should route directly to requirements capture or implementation planning. Repeat each case with and without the skill, scoring decision quality, factual grounding, user control, completeness of the final synthesis, unwanted file edits, question count, tool calls, tokens, and latency.
