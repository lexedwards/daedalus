# Feedback: Skill - decision-capture

## Evaluation Scope

This is a theory review, not an empirical evaluation. No prompt set, rubric, repeated trials, or no-skill baseline was provided, so the scores estimate design quality on a five-point scale rather than measured outcome uplift.

## Summary

The skill is concise, easy to maintain, and focused on a durable need: preserving consequential decisions without turning every implementation choice into an ADR. Its capture criteria and prohibition on deleting decision history provide useful discipline at very low context cost.

Its main weakness is workflow reliability. The creation flow can stop at offering an ADR even when the user asked for one, while the supersession flow does not explicitly create the replacement decision. Hard-coded document rules can also override an established repository ADR convention, and missing-context handling is not defined.

## Findings

### High: The creation workflow can fail to perform the requested action

The skill triggers when a user wants to preserve a decision, but the creation workflow says to "Only offer to capture important decisions." An agent can comply by proposing an ADR instead of writing it, despite the user already requesting capture. This conflicts with the later "Write the ADR" step and lowers procedural reliability.

Separate proactive and explicit-request behavior. When the skill notices a qualifying decision incidentally, it may offer capture; when the user explicitly requests an ADR, it should write one if the available evidence meets the capture criteria.

### High: Supersession does not define a complete lifecycle

The supersession workflow only says never to delete ADRs and to update the old ADR's status. It does not require creating the replacement ADR, assigning its sequence number, recording what it supersedes, or ensuring the old status points to the replacement that was actually written. An agent could therefore mark a decision as superseded without preserving its successor.

Define supersession as one atomic workflow: inspect both decisions, create the new ADR using repository conventions, link the new ADR back to the old one, and only then mark the old ADR as superseded by the new identifier.

### High: Local ADR conventions do not clearly take precedence

The skill says to gather existing decisions and follow the common file structure, but then mandates its own frontmatter, headings, location, flat layout, and numbering. Repositories commonly use different ADR templates, status fields, directories, and numbering schemes. Following the skill literally can introduce an incompatible parallel convention.

State that established repository conventions always win. Use `docs/adrs/`, the supplied template, and three-digit sequence numbering only when no local convention or user instruction exists.

### Medium: Missing or ambiguous context has no safe outcome

The opening instruction prohibits interviewing the user and says to use only what is known, but it does not explain what to do when alternatives, rationale, acceptance status, or consequences are unclear. Because the template requires a decision and rationale, an agent may infer facts or prematurely record an unsettled choice.

Require the agent not to invent missing context. If the known material cannot support a concise, accurate ADR, it should avoid writing one and identify the specific missing decision evidence. The skill should also define how to distinguish `proposed` from `accepted`.

### Medium: The content prohibitions are too broad for useful ADRs

The blanket ban on implementation details, code snippets, and references to specs or tasks can remove evidence needed to understand why a decision was made. This is especially limiting for deliberate deviations, constraints, and rejected alternatives, where a concise link to an authoritative requirement or existing interface may be essential.

Prohibit transient execution plans and excessive implementation detail instead. Permit concise technical evidence and durable references when they explain the decision context, while keeping the ADR focused on the decision rather than the work schedule.

### Medium: The trigger omits part of the implemented workflow

The description covers capturing decisions but not updating or superseding existing ADRs. Explicit prompts such as "supersede ADR 004" may therefore fail to trigger the skill even though it contains a dedicated supersession workflow.

Extend the description to include creating, updating, and superseding ADRs while retaining the importance and reversibility threshold.

## Recommended Next Evaluation

After resolving the workflow ambiguities, run an ablation with explicit creation requests, incidental decisions that should and should not prompt capture, incomplete decision context, repositories with existing ADR conventions, first-ADR repositories, and supersession requests. Repeat each case with and without the skill, scoring factual fidelity, convention adherence, correct trigger behavior, lifecycle completeness, unnecessary interaction, tokens, tool calls, and latency.
