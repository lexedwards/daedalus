# Feedback: Skill - code-crafting

## Evaluation Scope

This is a theory review, not an empirical evaluation. No prompt set, rubric, repeated trials, or no-skill baseline was supplied, so per the feedback guidance for reviewing skills without that evidence, this assesses design quality only and takes no corrective action on the skill itself.

## Summary

The skill captures a coherent, durable set of engineering preferences: trace before touching, ship one vertical slice, prove behavior via public interfaces, fix shared root causes, avoid speculative abstraction, and never let simplification erode validation/security/accessibility/error-handling. These are framework-neutral and unlikely to go stale, which is the skill's biggest asset.

Its two structural weaknesses recur across prior reviews of this same skill and remain unresolved: the trigger's "reviewing design choices" and "reviewing" language sits awkwardly next to a workflow (RED/GREEN/REFACTOR, `Implemented:` output) that assumes a change will actually be shipped, and the 247-line entry point repeats the same handful of constraints (small change, public-behavior testing, no speculative abstraction, verify-before-done) across six separate sections instead of stating them once and pushing detail to references.

## Findings

### High: Review-oriented trigger has no matching output shape

`When To Use` lists "Reviewing design choices" and "Choosing where logic should live" as valid entry points, but nothing downstream supports a pure review: the Craft Loop starts at `CHOOSE SLICE`, `Done Means` requires "the requested behavior works," and `Output Style` mandates `Implemented: / Verified: / Skipped:`. An agent invoked purely to weigh in on a design decision (no edit intended) is left to either fabricate an implementation step or violate the skill's own output contract.

Add a lightweight review branch (trace → identify tradeoffs → recommend, with a neutral output format) or narrow the trigger to only exclude ambiguity around review-only tasks.

### Medium: Duplication reduces context efficiency without adding new information

"Prefer the smallest correct change," "test behavior not implementation," and "verify before declaring done" each appear near-verbatim in `Core Principles`, `TDD: Green`, `Scope Discipline`, `Verification`, and `Done Means`. None of the repeats add a new constraint — they restate the same rule from a slightly different angle. On a one-line bug fix this is pure overhead: the agent must read all ~250 lines to extract guidance that could fit in a third of the space.

Consolidate each rule to a single authoritative location and cross-reference it elsewhere rather than restating it.

### Medium: TDD strictness is under-specified relative to its exceptions

The loop diagram implies RED is always executed, but the prose immediately qualifies it ("when practical"), and `Verification`/`Done Means` separately carve out exemptions for missing harnesses and trivial one-liners. Three different places soften the same rule without saying which one governs precedence, so two runs of the same task could reasonably diverge on whether a test is required.

A single explicit precedence statement (harness exists + non-trivial behavior → RED first; otherwise → cheapest durable check + stated gap) would remove this ambiguity in one place instead of three.

### Low: "Deep modules" and "least code first" read as competing defaults before resolution

Section 3 lists Ousterhout-style deep-module guidance and Unix-style minimalism as parallel `Prefer` bullets, then resolves the tension later with "deep modules only around one cohesive business concern." Moving the resolving sentence before the bullet lists would prevent a reader from provisionally adopting the wrong default mid-read.

## Rubric Notes

| Measure | Assessment |
| --- | --- |
| Trigger quality | Good recall for feature/bug/refactor work; the review-only trigger is under-supported by the workflow, hurting precision. |
| Outcome uplift | Principles should raise the floor on ad hoc coding tasks; unmeasured, and likely marginal where the host harness already enforces similar discipline. |
| Reliability | Feature/bug paths are well specified; TDD exceptions and the missing review branch introduce run-to-run variance. |
| Efficiency | Loop itself is efficient, but the repeated constraints and unconditional "broader verification" step add avoidable tokens on small tasks. |
| Procedural compliance | Rules are explicit and mostly followable, though the scattered TDD exceptions weaken strict compliance guarantees. |
| Safety | Explicit, named protections for validation, security, accessibility, data loss, and error handling — a real strength. |
| Context efficiency | Weakest dimension: long entry point, no progressive disclosure, same rules restated five-plus times. |
| Source alignment | Tool/framework-neutral; no stale API or platform-specific claims found. |
| Maintainability | Clear section headers aid navigation, but duplication raises the risk that a future edit updates one copy of a rule and misses others. |
| Durability | Strong: the guidance encodes lasting engineering judgment (root-cause fixes, behavior-focused tests, minimalism) rather than model-specific workarounds. |

## Recommended Next Evaluation

Once the review branch and single TDD-precedence rule are added, run an ablation across: small bug fixes, single-behavior feature slices, refactors, design-only reviews, analysis-only code reviews with no intended edit, tasks with no test harness, and negative/documentation-only prompts. Score correctness, unnecessary edits, test relevance, tool calls, tokens, latency, and procedural compliance with and without the skill loaded.
