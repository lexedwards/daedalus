# Feedback: Skill - code-crafting

## Evaluation Scope

This is a theory review, not an empirical evaluation. No prompt set, rubric, repeated trials, or no-skill baseline was provided, so the scores estimate design quality on a five-point scale rather than measured outcome uplift.

## Summary

The skill encodes durable, generally sound engineering preferences: trace the real path, make the smallest complete change, test observable behavior, fix shared root causes, and avoid speculative abstractions. Its strongest value is the coherent end-to-end craft loop.

Its likely marginal value is reduced by its size, repetition, and overlap with common harness-level coding instructions. The largest reliability issue is that the frontmatter says to use the skill when "reviewing code", while most procedures require editing, TDD, and an `Implemented` output. Review tasks can therefore trigger a workflow they cannot comply with.

## Findings

### High: The review trigger does not have a compatible workflow

The frontmatter includes "reviewing code", but `When To Use` narrows this to "reviewing design choices", and the remaining sections assume a change will be implemented. The craft loop requires TDD phases, `Done Means` requires behavior to work, and `Output Style` starts with `Implemented`.

This ambiguity harms trigger precision and procedural compliance. Either remove general code review from the description or add a short review branch with review-appropriate actions and output. Removing the trigger is preferable if another review-specific agent or skill already owns that task.

### High: The full entry point is too large and repetitive

The skill repeats the same ideas across `Core Principles`, the numbered workflow, `Testing Guidance`, `Scope Discipline`, `Verification`, and `Done Means`. Minimal changes, public behavior, avoiding speculative abstractions, and verification each appear several times.

This increases token and attention cost on every invocation, including simple fixes where most guidance is unused. Keep the entry point focused on trigger rules, the craft loop, and non-negotiable constraints. Move detailed module-design and testing guidance into references that are loaded only when those decisions arise.

### Medium: TDD requirements are internally inconsistent

The craft loop presents `TDD: RED` as unconditional, while the detailed instruction says to write a failing check "when practical", and `Verification` exempts trivial one-liners from new tests. An agent cannot reliably infer which statement takes precedence.

Make the loop conditional: use red-green-refactor for observable behavior changes when a runnable harness exists; otherwise use the smallest durable check available and state the gap. Define examples of practical exceptions, such as documentation-only changes, missing harnesses, or non-reproducible external failures.

### Medium: Verification scope can cause unnecessary work

The skill correctly says to run the narrowest relevant check first, but then requires "broader verification before declaring done" for every slice. That can encourage expensive full-suite runs even when a targeted check fully covers a low-risk change.

Tie broader verification to affected scope and regression risk. Require the relevant existing checks, then escalate only when the change crosses boundaries or targeted checks reveal a reason.

### Medium: The mandated output shape is too rigid

The `Implemented / Verified / Skipped` template is useful for implementation handoffs but poorly fits design reviews, investigations, or tasks where no change is appropriate. It may also duplicate a host harness's response-style instructions.

Make the template implementation-specific or remove it. Outcome reporting is usually better owned by the harness so the skill can focus on engineering decisions.

## Recommended Next Evaluation

After tightening the trigger and entry point, run an ablation across small bug fixes, feature slices, refactors, design reviews, documentation edits, and analysis-only code reviews. Repeat each prompt with and without the skill, scoring correctness, unnecessary edits, test relevance, tool calls, tokens, latency, and compliance. Include negative prompts to confirm that documentation and analysis-only work do not trigger an implementation workflow.
