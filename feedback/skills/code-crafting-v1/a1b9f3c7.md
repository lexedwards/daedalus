# Feedback: Skill - code-crafting

## Evaluation Scope

This is a theory review, not an empirical evaluation. The feedback guidance states that a skill supplied without a prompt set or eval suite should be reviewed as theory with no action taken, so no ablation, repeated trials, or no-skill baseline was run. Scores estimate design quality on a five-point scale rather than measured outcome uplift.

## Summary

The skill encodes a strong, durable engineering discipline: trace the real path first, deliver one vertical slice, prove behavior through public interfaces, fix shared root causes, and verify before stopping. The "lazy ladder," the real-over-fake test preference, and the explicit list of things simplification must never remove (validation at trust boundaries, security, accessibility, data-loss prevention, error handling) are the highest-value parts. These are framework-neutral and should age well.

The two weaknesses that most limit its practical value are structural, not conceptual. First, the trigger advertises code review and design review, but every downstream section assumes an implementation is being written, so review-only tasks have no supported path. Second, the entry point is long (247 lines) and repeats its core constraints across six sections without progressive disclosure, which weakens context efficiency for the many small tasks the skill will run on.

## Findings

### High: The review trigger has no matching workflow

The description and `When To Use` both invite the skill for "reviewing code" and "reviewing design choices," but the `Craft Loop`, the numbered RED/GREEN/REFACTOR steps, `Done Means`, and `Output Style` are all written for producing a change. A review task has no slice to choose, no failing check to write, and no `Implemented:` line to report. An agent that loads this skill for a review is pushed toward either editing code it was only asked to assess or forcing an analysis into an implementation-shaped template.

Either drop review from the trigger, or add a dedicated review branch with its own trace, evidence-gathering, findings, and neutral output steps, and distinguish design review from analysis-only code review.

### High: The entry point duplicates its constraints and lacks progressive disclosure

"Smallest correct change," "public interface over implementation detail," "no speculative abstraction," "scope discipline," and "verify before done" each recur across `Core Principles`, the numbered loop, `Testing Guidance`, `Scope Discipline`, `Verification`, and `Done Means`. The module-design vocabulary and the test taxonomy are genuinely useful, but loading all of it on every bug fix or one-line change is costly and dilutes the non-negotiable rules.

Keep the entry point to the trigger, the core loop, and the safety constraints. Move the module-depth discussion and the detailed testing taxonomy into `references/` files pulled in on demand, and remove repeated wording. The repo's own AGENTS.md advises keeping `SKILL.md` concise and pushing rarely needed detail into reference files.

### Medium: TDD is simultaneously mandatory and conditional

The `Craft Loop` diagram presents `TDD: RED -> GREEN -> REFACTOR` as the standard spine, but the prose softens it: RED applies "when practical," `Verification` allows "the smallest reliable manual check" when no harness exists, and `Done Means` exempts "trivial one-liners" from a new test. These qualifications are reasonable, but their precedence is never stated, so two agents can justify opposite behavior on the same task.

State one order explicitly: use red-green-refactor for behavior changes when a runnable harness exists; otherwise make the cheapest durable check and state the gap; skip a new test only for trivial one-liners. This turns three scattered exceptions into a single rule.

### Medium: The mandated output format only fits a completed change

`Output Style` requires `Implemented / Verified / Skipped`. That fits a finished code change but not a design review, an investigation, a blocked task, or a deliberate decision not to edit — all of which the trigger admits. The `Skipped` line also risks boilerplate and can collide with the host harness's own response formatting.

Make the format conditional on implementation work, or replace it with a neutral outcome-and-evidence statement that also covers reviews and no-change conclusions.

### Low: "Deep modules" and "least code / plain functions first" pull in opposite directions

The skill blends two design traditions: Ousterhout-style deep modules (substantial behavior behind a narrow interface) and Unix/least-code minimalism ("plain functions before classes," "existing interfaces before new ones"). It reconciles them with "deep modules only around one cohesive business concern," which is the right resolution, but a reader scanning the `Prefer`/`Avoid` lists may see the two pulls before the reconciling clause. Consider stating the reconciliation up front so the guidance reads as one principle rather than two competing ones.

### Low: Grammar inconsistency in the Good tests list

Under `Good tests:`, the first item "Describes the product behavior..." is third-person singular while every sibling bullet is imperative ("Test state...", "Name the behavior...", "Keep expected values..."). Change it to "Describe the product behavior, not the underlying code." for parallelism.

## Recommended Next Evaluation

Once a review branch and a single test/verification precedence rule are added, run an ablation across small bug fixes, single-behavior feature slices, refactors, design reviews, analysis-only code reviews, tasks with no test harness, and negative prompts (documentation-only and static-content edits that should not trigger an implementation workflow). Repeat each prompt with and without the skill, scoring correctness, unnecessary edits, test relevance, procedural compliance, tool calls, tokens, and latency.
