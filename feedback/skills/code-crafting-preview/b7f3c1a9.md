# Feedback: Skill - code-crafting-preview

## Evaluation Scope

Theory review only. No prompt set, rubric, repeated trials, or no-skill baseline was supplied, so per `feedback/README.md` ("review the theory and do not take action") these scores estimate design quality from reading `SKILL.md` (151 lines) and its five references (37-57 lines each), not measured outcome uplift. No corrective edits were made. Per the reviewer's instruction, trigger overlap with the sibling `code-crafting` skill is treated as out of scope because the preview is intended to replace it; trigger-quality is therefore assessed on the skill's own merits, not on the collision.

## Summary

This is a strong, near-ship-ready skill. It selects a mode before doing detailed work — implementation/refactor, bug fix, code review, design review, and no-change/documentation — and states plainly that review modes do not edit code unless the user asks. That mode split is the design's defining strength and resolves the "review request drives an implementation loop" failure common in less-structured coding skills.

Structure conforms to the required layout: kebab-case directory, uppercase `SKILL.md` under the 500-line cap, frontmatter `name` matching the directory, a single-line description, and five focused `references/*.md` files loaded on demand. Core guidance — trace before changing, smallest correct slice, seam only for real variation, behavior-first proof with an explicit precedence when no harness exists, risk-based verification escalation, and the lazy ladder — is framework-neutral and durable. Safety carve-outs (validation, security, accessibility, data-loss prevention, error handling) are explicitly protected from minimalism and refactoring pressure.

The findings below focus on internal consistency issues I did not see fully captured in prior reviews: an output-template mismatch between `SKILL.md` and the review reference, and a surface contradiction around the documentation mode.

## Findings

### Medium: Review output template in `SKILL.md` omits a field its own reference requires

`SKILL.md` "Done and Output" gives the review template as four fields — `Assessment / Evidence / Recommendation / Residual risk`. But `references/review-workflows.md` "Review Output" defines five fields, adding `Findings: [ordered findings, if any]` between Evidence and Recommendation. An agent that reads only the entry point will emit a review report with no dedicated findings line, even though "Review Evidence" in `SKILL.md` and the finding format in the reference both stress ordered, evidence-backed findings as the core deliverable. This is a concrete source-of-truth divergence, not a stylistic nuance, and is the main reason procedural-compliance is a 3 rather than 4. Recommendation (do not action in a theory review): align the two templates so the entry-point review shape includes `Findings`. Confidence: high.

### Low: Documentation mode reads as a contradiction without a one-line rationale

"When To Use" says "Do not use it for pure documentation or static-content work unless the user asks for engineering guidance," while "Choose a Mode" lists a fifth mode: "No-change or documentation task: assess applicability, make no unrelated edits, and report the conclusion." Both are individually correct — the mode is a graceful back-out path for when the skill fires but the task turns out to be docs/no-change — but the entry point never says so, so the two statements can read as conflicting. A short clarifying clause ("if the skill activates on a task that is actually documentation-only, use this mode to back out cleanly") would remove the apparent contradiction. Confidence: medium.

### Low: No output shape for the no-change / documentation mode

"Done and Output" provides templates for implementation and review, but the fifth mode has no matching output shape. An agent that concludes the skill does not apply must improvise its report format. The review template is a plausible fit, but that mapping is left implicit. (Corroborates a prior review; still unresolved.) Confidence: low.

### Low: "Run the relevant check after each refactor step" is categorical against the skill's own efficiency stance

"Implement and Refactor" instructs running the relevant check "after each refactor step," while the rest of the skill favors the cheapest sufficient check and stopping once the outcome is satisfied. For a sequence of small, safe, local cleanups this can add avoidable tool calls and latency. Scoping the rule to each behaviorally meaningful or risk-changing increment would keep the intent without the per-step cost. Confidence: medium.

### Low: `SKILL.md` restates reference content (context-efficiency drag, sync burden)

The `Prove the Behavior` precedence overlaps closely with `Red-Green-Refactor` in `testing-and-tdd.md`, the `Verify` section restates most of the `verification.md` risk table in prose, and the lazy ladder appears verbatim in both `SKILL.md` and `change-strategy.md`. This is a deliberate progressive-disclosure trade-off, but it is the main avoidable token cost in the entry point and creates a synchronization burden — the output-template drift in the Medium finding is exactly the kind of divergence this duplication invites. Confidence: medium.

## Recommendation

Treat this as a strong replacement candidate for `code-crafting`. The highest-value pre-ship fix is aligning the review output template in `SKILL.md` with `review-workflows.md` (add `Findings`), then trimming the duplicated Prove/Verify/lazy-ladder passages to pointers so the two copies cannot drift again. Add a one-line output shape and rationale for the no-change/documentation mode. After that, run an ablation across implementation slices, bug fixes, refactors, code reviews, design reviews, no-harness tasks, and documentation-only negative prompts, comparing correctness, unnecessary edits, finding quality, procedural compliance, tool calls, tokens, and latency with and without the skill.

## Residual Risk

Without repeated isolated trials and a no-skill baseline, measured outcome uplift, reliability variance, and actual context-cost savings from progressive disclosure remain unverified.
