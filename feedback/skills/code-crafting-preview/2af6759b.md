# Feedback: Skill - code-crafting-preview

## Evaluation Scope

Theory review only. No prompt set, rubric, repeated trials, or no-skill baseline was supplied, so per `feedback/README.md` ("review the theory and do not take action") the scores estimate design quality from reading `SKILL.md` and its four references, not measured outcome uplift. No corrective edits were made to the skill.

## Summary

The skill is well constructed. It selects a mode up front — implementation/refactor, bug fix, code review, design review, and no-change/documentation — before prescribing any detailed steps, and it states plainly that review modes do not edit code unless the user asks. That mode split is the design's biggest strength: it resolves the recurring "review trigger with no review output" problem seen in the sibling `code-crafting` skill.

Structure conforms to the required layout: kebab-case directory, uppercase `SKILL.md` (137 lines, under the 500-line cap), frontmatter `name` matching the directory, a single-line description, and four focused `references/*.md` files (37-57 lines each) loaded on demand. Core engineering guidance — trace before changing, smallest correct slice, seam only for real variation, behavior-first proof with an explicit precedence when no harness exists, and risk-based verification escalation — is framework-neutral and durable. Safety carve-outs (validation, security, accessibility, data-loss prevention, error handling) are explicitly protected from minimalism and refactoring pressure.

The main new observation in this review is external: `code-crafting-preview` ships alongside `code-crafting` with a near-identical trigger surface, which is a trigger-quality and maintainability risk that a single-skill read does not surface.

## Findings

### Medium: Trigger collision with the co-installed `code-crafting` skill

`skills/` contains both `code-crafting` and `code-crafting-preview`, and their descriptions cover the same task space (implementing, fixing, refactoring, reviewing). Two skills competing for the same activation conditions degrade trigger precision: the harness may load either, both, or neither depending on wording, and an ablation that isolates the preview's uplift becomes hard to run because the baseline skill can also fire. Evidence: `code-crafting` description ends "Use when implementing, fixing, refactoring, or reviewing code"; the preview covers "pragmatic implementation, bug fixing, refactoring, and code or design review." Recommendation (do not action in a theory review): decide whether the preview supersedes or coexists with the original, and if it coexists, differentiate the trigger scope explicitly (e.g., reserve one for review-only work) so selection is deterministic. Confidence: high that the overlap exists; medium on real-world selection impact without trials.

### Low: Preview description lacks an explicit "Use when" trigger clause

`code-crafting`'s description ends with a direct imperative ("Use when implementing, fixing, refactoring, or reviewing code"). The preview's description is phrased purely as a capability statement ("Guide pragmatic implementation, bug fixing, refactoring, and code or design review ...") with no explicit activation clause. Capability phrasing can weaken recall relative to an imperative trigger. This is a low-confidence stylistic observation, not a defect. Confidence: low.

### Low: No output shape for the no-change / documentation mode

`Done and Output` provides two templates (implementation: `Implemented/Verified/Remaining`; review: `Assessment/Evidence/Recommendation/Residual risk`). The `Choose a Mode` list adds a fifth mode — "No-change or documentation task: assess applicability ... and report the conclusion" — but no matching output shape is given in `SKILL.md`. An agent that concludes the skill does not apply is left to improvise its report format. The review template is a reasonable fit, but that mapping is implicit. Confidence: low.

### Low: `SKILL.md` restates reference content (context-efficiency drag, sync burden)

The `Prove the Behavior` precedence list overlaps closely with `Red-Green-Refactor` in `testing-and-tdd.md`, and the `Verify` section restates most of the `verification.md` risk table in prose. This is a deliberate progressive-disclosure trade-off rather than a defect, but it is the main avoidable token cost in the entry point and creates a small synchronization burden if one copy is edited without the other. (Previously noted in prior reviews; repeated here because it is unresolved.) Confidence: medium.

## Recommendation

Treat this as a strong, near-ship-ready refinement of `code-crafting`. Before empirical work, resolve the coexistence question with the original skill so triggers are deterministic and an ablation is meaningful. Then run an ablation across implementation slices, bug fixes, refactors, code reviews, design reviews, no-harness tasks, and documentation-only negative prompts, comparing correctness, unnecessary edits, finding quality, procedural compliance, tool calls, tokens, and latency with and without the skill. Minor polish worth considering: add a one-line output shape for the no-change mode, and trim the Prove/Verify summaries in `SKILL.md` to pointers into their references.

## Residual Risk

Without repeated isolated trials and a no-skill baseline, measured outcome uplift, reliability variance, and actual context-cost savings from progressive disclosure remain unverified. The trigger-collision impact in particular cannot be quantified without live selection data.
