# Feedback: Skill - create-a-service

## Assessment

The skill has a strong decision structure, a precise trigger, and useful
progressive disclosure. Its provider-first classification, staged acceptance
gates, lifecycle boundaries, least-privilege defaults, and prohibition on
unrequested infrastructure operations should materially reduce common homelab
implementation errors.

The main weakness is source alignment. Several categorical instructions do not
match the repository evidence they cite, and two designated examples would lead
an agent toward patterns the skill itself prohibits. No prompt set, baseline,
repeated trials, or ablation evidence was supplied, so trigger precision,
outcome uplift, reliability, and execution cost cannot be confirmed. Scores for
those measures assess the theory only.

## Findings

### High: The Proxmox VM path depends on a Debian template the catalogue cannot manage

**Location:** `references/proxmox-vm.md:7-16`; `services/image-catalogue/README.md:7-8,61-65`; `services/image-catalogue/variables.tf:165-177`

**Evidence:** The VM reference says to clone a reviewed Debian 13 template
managed by `services/image-catalogue/`. The catalogue is intentionally empty and
accepts only Amazon Linux 2023, Fedora 44, Rocky Linux 10, and Ubuntu 26.04
release channels. Debian 13 cannot currently be declared through its
`cloud_images` input.

**Impact:** An agent can select the preferred Proxmox VM branch and then reach an
implementation prerequisite that the referenced repository root cannot
produce. It may invent an unsupported catalogue entry, assume an unmanaged
template exists, or leave the service incomplete.

**Recommendation:** Either add and validate a Debian 13 catalogue channel before
making it the default, or state that the agent must use an existing reviewed
catalogue image compatible with the workload. Treat Debian 13 as preferred only
after the catalogue can authoritatively supply it.

**Confidence:** High

### High: The designated Incus Compose example violates the skill's own lifecycle rules

**Location:** `references/incus.md:14-21`; `references/lifecycle-and-operations.md:43-51`; `services/uptime-kuma/README.md:83-94`; `services/uptime-kuma/cloud-init/user-data.tftpl:9-26`

**Evidence:** The Incus reference points to Uptime Kuma for Compose and protected
data. Its runbook upgrades by deleting the container and issuing an imperative
`docker run`, despite the skill prohibiting that lifecycle. Its Compose service
also omits the required capability reduction, `no-new-privileges`, and bounded
logging controls, and cloud-init starts Compose directly rather than through a
dedicated systemd unit.

**Impact:** Agents are likely to copy the concrete example over the abstract
rule, producing services that fail the skill's security and lifecycle gates.
This also increases run-to-run variance because the reference does not identify
which parts are approved and which are legacy exceptions.

**Recommendation:** Fix the Uptime Kuma baseline before designating it as the
Compose example. Until then, cite it only for custom-volume persistence and
explicitly prohibit copying its container lifecycle. Point Compose hardening to
a conforming tracked example.

**Confidence:** High

### High: A "reviewed saved plan" is not operationally defined

**Location:** `SKILL.md:49-50,184-186`; `services/hello-world/Makefile:35-40`; `.gitignore:7`

**Evidence:** The skill requires apply operations to use a reviewed saved plan,
but does not define freshness, provenance, or what review must observe. The
representative `make apply` target only checks that an ignored plan file exists
before applying it. An old plan can therefore satisfy the mechanical workflow.
The instruction not to inspect saved plans to discover private values also sits
beside the requirement to review one without explaining the distinction.

**Impact:** An explicitly requested apply can consume a stale or differently
generated plan while appearing compliant. This is the highest-consequence path
in the skill and should not depend on an undefined adjective.

**Recommendation:** Define an acceptable plan as one generated for the current
configuration and inspected in the current workflow, with no intervening
configuration changes. Permit `tofu show` for that review while prohibiting the
agent from reproducing private values. Require explicit confirmation when the
user supplies a pre-existing plan that cannot be proven current.

**Confidence:** High

### Medium: The privacy boundary is too broad and internally inconsistent

**Location:** `SKILL.md:36-40,153-158`; `references/lifecycle-and-operations.md:8-28`; `references/incus.md:27-31`; `references/proxmox.md:24-28`

**Evidence:** The skill classifies all network, storage, identity, and endpoint
values as private and says never to document real values. It then records real
host roles, project names, pool names, and bridge conventions as implementation
guidance. Current tracked `terraform.tfvars.example` files also contain concrete
infrastructure examples, so the instruction conflicts with both the skill's
references and repository convention.

**Impact:** Agents may redact harmless architecture identifiers, refuse useful
documentation, or inconsistently decide which repository evidence may be read
and reported. The ambiguity also complicates plan review and makes procedural
compliance difficult to evaluate.

**Recommendation:** Separate credentials and secret material from
environment-specific infrastructure identifiers. Define which identifiers may
be documented as architecture, which may be read but not repeated, and which
must never enter tracked files. Keep the stronger handling rules for secrets,
state, plans, and ignored local configuration.

**Confidence:** High

### Medium: `security.nesting` is a blanket exception without workload evidence

**Location:** `SKILL.md:43-45,160-161`; `references/incus.md:35-45`; `services/hello-world/main.tf:39-46`

**Evidence:** The core skill permits kernel and security exceptions only for a
stated workload requirement, but the Incus branch requires
`security.nesting = "true"` for every Debian 13 systemd container. The smallest
native service copies the setting without documenting why its workload needs
the larger kernel surface.

**Impact:** The branch weakens its least-privilege model by converting an
inherited repository setting into a universal requirement. Agents have no gate
for proving that the exception is necessary.

**Recommendation:** Make nesting conditional on a demonstrated guest or
workload requirement. If the Micro Node genuinely requires it for all Debian 13
systemd guests, document the host-specific reason and the evidence supporting
that policy.

**Confidence:** Medium

### Medium: The capacity gate has no offline completion path

**Location:** `SKILL.md:29-30,93-95,107-109`; `hosts/compute/README.md:3-5`; `hosts/store/README.md:3-5`

**Evidence:** Placement requires confirmation of current capacity, networking,
storage, images, and devices, while infrastructure contact is prohibited unless
the user explicitly requests it. The host documents describe roles and provider
setup but contain no current utilization, bridge, datastore, device-allocation,
or cluster-wide guest-ID inventory.

**Impact:** A new service cannot normally pass the placement gate from tracked
evidence alone. Different agents may silently assume capacity, block
indefinitely, or contact infrastructure without authorization.

**Recommendation:** Add an explicit fallback: ask the user for the missing
inventory, request authorization for a read-only query, or record placement as
provisional and stop before implementation. Specify which path is expected for
a normal offline task.

**Confidence:** High

### Low: Some "current tracked" Proxmox baselines are not tracked at review time

**Location:** `SKILL.md:36-38`; `references/proxmox.md:7-17`

**Evidence:** The Proxmox reference treats `hosts/compute/`, `hosts/store/`, and
`services/observability-warehouse/` as current repository evidence. At review
time all three roots are untracked, while the core workflow explicitly directs
the agent to rely on tracked files.

**Impact:** The skill presents candidate worktree content as established
convention. This is likely temporary, but until those roots are committed the
source hierarchy is contradictory.

**Recommendation:** Commit the baselines with the skill, or label them as
candidate examples that must not override tracked conventions.

**Confidence:** High

## Strengths

- The frontmatter trigger is specific to OpenTofu-managed homelab services and
  includes a valuable negative rule against inferring platforms from generic
  guest-provisioning evidence.
- The trace, establish, classify, boundary, implementation, and verification
  stages give agents a clear decision order rather than a flat checklist.
- Provider and resource evidence correctly outrank cloud-init, systemd, Docker,
  and directory placement when classifying an existing service.
- Progressive disclosure is effective: the 197-line entry point delegates
  platform and lifecycle details to five focused references.
- The skill handles replacement, durable data, enrollment, backup ownership,
  cloud-init limitations, and operator responsibilities more thoroughly than
  most infrastructure-generation guidance.
- The Proxmox LXC branch appropriately admits that no local application
  bootstrap convention exists and prohibits hiding remote execution inside
  OpenTofu.
- All explicit skill and reference paths exist, frontmatter and naming conform
  to the required structure, and Markdown lint passes.

## Recommendation

Retain the staged workflow, provider-first classification, and progressive
disclosure structure. Before relying on the skill for implementation, resolve
the Debian catalogue gap, replace or constrain the non-conforming Compose
example, and define the saved-plan review invariant. Then clarify the privacy,
nesting, and offline-capacity rules.

Create an ablation suite with positive prompts for new Incus, Proxmox VM,
Proxmox LXC, appliance, existing-service modification, and explicit apply work.
Include negative prompts for generic Docker, systemd, cloud-init, and unrelated
OpenTofu tasks. Compare repeated skilled and unskilled runs on placement
accuracy, gate compliance, secret handling, complete service structure,
validation behavior, tool calls, tokens, and latency.

## Residual Risk

Without isolated repeated trials, there is no evidence that the additional
gates improve completion quality enough to offset their context and interaction
cost. The unresolved source conflicts make the current theoretical reliability
lower than the skill's strong structure initially suggests.
